# Платежи в MoveX GO

Документ описывает, как в системе движутся деньги, какие платёжные системы
подключены и что нужно сделать, чтобы включить их на бою.

## Как устроен денежный контур

```
клиент пополняет баланс  →  оформляет заказ  →  деньги заморожены (escrow)
                                                        │
                        владелец подтвердил ─────────────┤ деньги всё ещё заморожены
                                                        │
                        заказ завершён ──────────────────┤ клиента списывают
                                                         ├─ владельцу 90%
                                                         └─ платформе 10% (budget_reserves)
                                                        │
                        владелец запрашивает вывод ──────┘ payout_requests
```

Три правила, которые нельзя нарушать:

1. **Цену считает только сервер.** `services/pricing_service.py`. `total_amount`
   и `commission` из запроса игнорируются. Формула обязана совпадать с расчётом
   в `rent_equipment_page.dart`.
2. **Баланс пополняется только по подтверждению платёжной системы.** Заявка
   всегда создаётся в статусе `pending`. Список разрешённых способов —
   `SELF_SERVICE_PAYMENT_METHODS` в `balance_service.py`. Добавлять туда способ
   можно, только если по нему приходит колбэк с подтверждением оплаты.
3. **При завершении заказа деньги списываются с баланса клиента**, а не только
   размораживаются. В ветках отказа и отмены — наоборот.

## Click

Реализован в `services/click_service.py`, эндпоинты `/balance/click/prepare`
и `/balance/click/complete`.

Ключи в `.env`:

```
CLICK_MERCHANT_ID=
CLICK_SERVICE_ID=
CLICK_SECRET_KEY=
CLICK_MERCHANT_USER_ID=
CLICK_RETURN_URL=movexgo://payment/success
```

Подпись: `md5(click_trans_id + service_id + secret_key + merchant_trans_id + amount + action + sign_time)`.

## Payme (Paycom)

Реализован в `services/payme_service.py`, один эндпоинт **`/payments/payme`** —
именно этот адрес указывается в кабинете Payme.

Ключи в `.env`:

```
PAYME_MERCHANT_ID=          # идентификатор кассы
PAYME_KEY=                  # ключ кассы (боевой)
PAYME_TEST_KEY=             # ключ для песочницы
PAYME_TEST_MODE=false
PAYME_ACCOUNT_FIELD=transaction_id   # как называется поле счёта в кабинете
PAYME_RETURN_URL=movexgo://payment/success
```

Особенности протокола, которые уже учтены:

- авторизация `Authorization: Basic base64("Paycom:" + ключ)`, иначе `-32504`
- суммы приходят **в тийинах**, в базе хранятся в сумах
- состояния: `1` создана, `2` проведена, `-1` отменена, `-2` отменена после проведения
- повторные запросы идемпотентны — Payme проверяет это на сертификации
- неоплаченная транзакция старше 12 часов автоматически отменяется
- отмена после проведения списывает деньги обратно, но **блокируется**, если
  клиент успел их потратить — иначе баланс ушёл бы в минус

Проверка: `venv/bin/python tests/verify_payme.py` — 33 теста, включая те
сценарии, которые Payme гоняет при подключении.

## Сплит — разделение платежа 90/10

Payme умеет делить платёж сам: в ответе `CheckPerformTransaction` и
`CreateTransaction` возвращается массив `receivers`:

```json
"receivers": [{ "id": "5305e3bab097f420a62ced0b", "amount": 500000 }]
```

`id` — идентификатор получателя в Payme, `amount` — в тийинах. Идентификатор
владельца техники хранится в `users.payme_receiver_id`.

Режим переключается настройкой **`SPLIT_MODE`**:

| Значение | Что происходит | Когда выбирать |
|---|---|---|
| `escrow` (по умолчанию) | Деньги полностью приходят платформе и лежат до завершения заказа. Владельцу переводятся потом, через заявку на вывод. | Клиент защищён: если техника не приехала, деньги вернутся. |
| `on_payment` | Payme сразу делит платёж: 90% на счёт владельца, 10% платформе. | Меньше денег на счету платформы, проще с налогами. Но escrow-защиты нет — владелец получает деньги до выполнения работы. |

По умолчанию стоит `escrow`, потому что это то, что продукт обещает клиенту
сейчас. Переключение на `on_payment` — продуктовое решение, а не техническое.

Если у владельца не заполнен `payme_receiver_id`, разделение пропускается и
деньги идут обычным путём — заказ от этого не ломается.

## Rahmat

Публичной документации merchant API у Rahmat нет — интеграцию писать не по
чему. Когда появится договор и доступ к кабинету, добавлять её нужно так же,
как Payme: отдельный сервис + запись в `SELF_SERVICE_PAYMENT_METHODS`.

## Вывод денег владельцу

`payout_requests` + эндпоинты `/payouts/*`. Раньше такой возможности не было
вообще: баланс владельца рос, а забрать его было нечем.

| Шаг | Что с деньгами |
|---|---|
| Владелец создал заявку | Сумма уходит в `frozen_balance` — второй раз те же деньги не запросить |
| Админ отметил «выплачено» | Списывается с баланса, заморозка снимается, создаётся транзакция `withdrawal` |
| Админ отклонил | Только снимается заморозка, деньги остаются у владельца |

Минимальная сумма — 50 000 сум (`MIN_PAYOUT_SUM`).

Номер карты хранится целиком, потому что без него не сделать перевод, но
**в API он никогда не возвращается целиком** — только `•••• 1234`. Сам перевод
делается вручную; система только ведёт учёт.

Проверка: `venv/bin/python tests/verify_payouts.py` — 26 тестов.

## Что нужно для запуска на бою

1. Получить мерчант-аккаунты в Click и Payme, вписать ключи в `/opt/movex_go/.env`
   на сервере (в systemd-юните уже стоит `EnvironmentFile`).
2. В кабинете Payme указать адрес `https://movex.004.uz/payments/payme` и
   имя поля счёта, совпадающее с `PAYME_ACCOUNT_FIELD`.
3. Прогнать сертификацию Payme — сценарии из `tests/verify_payme.py` покрывают
   то, что там проверяют.
4. Решить по `SPLIT_MODE`. Если `on_payment` — собрать у владельцев техники
   их идентификаторы получателей Payme.
