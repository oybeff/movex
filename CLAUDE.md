# MoveX GO

Платформа аренды строительной техники (Узбекистан). Клиент находит и арендует технику,
владелец сдаёт её и управляет парком.

**Прод — `https://movexgo.uz`**, поднят 4 сентября 2026 на VPS `189.74.98.45`
(Eskiz, Ubuntu 24.04, 2 ядра / 2 ГБ / 40 ГБ). Код в `/opt/movex`, служба
`movex-api` под systemd в двух воркерах, админка на `/panel/`, сертификат
Let's Encrypt на `movexgo.uz` и `www`. Домен делегирован на A-Host
(`rdns1-3.ahost.uz`) — зону править ТАМ, а не там, где удобнее: правка в
чужой панели сохраняется и не работает, это уже стоило времени.
Разворачивалось комплектом `deploy/`. Прежний адрес `movex.004.uz` остался
на старом сервере и к этому проекту больше не относится.

## Структура

```
movex/
├── backend/   FastAPI + PostgreSQL + Alembic   — основной API
├── admin/     чистый PHP 7.4 + PDO            — админ-панель (ходит в БД напрямую)
├── mobile/    Flutter 3.8                     — приложение iOS + Android
└── docs/      выгрузка .md из исходных архивов (deploy-гайды, платежи)
```

Три части были отдельными GitHub-репозиториями (`movex_go_backend`, `movex_go_admin`,
`movex_go_mobile`), собраны в один монорепо 30 августа 2026. Git-истории не сохранилось —
первый коммит здесь и есть точка отсчёта.

Монорепо: **`oybeff/movex`** (приватный), ветка по умолчанию `main`.
Пушится по HTTPS через токен `gh`, а не по SSH: ключ на машине разработки
принадлежит другому аккаунту (`Avenir-Soft`), и `git push` по SSH уходил
не туда. Серверу отдаётся отдельный ключ развёртывания только на чтение —
`deploy/README.md`.

## Домен и роли

Роли пользователя: **client**, **owner**, **admin** (`backend/app/core/roles.py`).

- **client** — каталог техники, аренда с выбором точки на карте, чат с владельцем,
  история заказов, баланс и платежи
- **owner** — дашборд, свой парк техники (добавить/редактировать), заказы, статистика,
  платежи, франшиза
- **admin** — только через PHP-панель, не через мобилку

Кроме ролей у пользователя есть два флага состояния (`app/core/account_state.py`):
**заблокирован** — не может войти вообще, и выданный до блокировки токен умирает
сразу (проверка в `get_current_user`, иначе он работал бы ещё 30 дней);
**заморожен** — входит и всё видит, но не может заказывать, предлагать, размещать
объявления и выводить деньги. Ставится из админки, к админам не применяется.

### Четыре способа свести людей друг с другом

Они не взаимозаменяемы, и путать их нельзя:

| | откуда берётся | кто выбирает | деньги |
|---|---|---|---|
| **Каталог** | техника из справочника | клиент выбирает машину | эскроу |
| **Заявки** `/requests` | тип из справочника | владельцы предлагают цену, клиент выбирает | эскроу при выборе |
| **Объявления** `/listings` | свободный текст | берут или предлагают цену, автор выбирает | эскроу при подтверждении |
| **Материалы** `/materials` | товар из справочника | клиент выбирает товар и количество | эскроу |

Объявления существуют ровно для того, чего нет в справочнике («нужны три
грузчика»), поэтому `equipment_type` там необязателен.

**Деньги в объявлениях появились 5 сентября 2026** и работают ровно как в
заказах: подтверждение исполнителя ЗАМОРАЖИВАЕТ сумму на балансе автора,
завершение списывает её и переводит исполнителю за вычетом комиссии, отказ
и отмена только снимают заморозку. Комиссию платит исполнитель — как и в
заказах, её платит тот, кто получает деньги. Ставка ОБЩАЯ с заказами
(`commission_mode` / `commission_fixed` / `commission_percent`), вторая
ставка не заводится сознательно: две разошлись бы.

Сумма берётся из бюджета объявления («взять») либо из цены принятого
предложения и пишется в `listings.agreed_price` вместе с `listings.commission`
В МОМЕНТ ПОДТВЕРЖДЕНИЯ — иначе смена ставки в админке переписала бы историю.
Объявление без бюджета подтвердить через «взять» нельзя: замораживать нечего,
такому объявлению нужен путь предложений.

Комиссия объявлений попадает в ту же таблицу `budget_reserves`, что и у
заказов: у неё теперь `order_id` ИЛИ `listing_id`, ровно одно из двух
(`check_budget_reserve_source`). `admin/budget.php` из-за этого ходит
LEFT JOIN'ами — при INNER JOIN строки объявлений молча выпадали бы из списка,
а в итог попадали, и цифры на странице расходились бы.

**Объявления двусторонние и от роли не зависят.** Клиент пишет «нужны три
грузчика», владелец пишет «завтра свободен экскаватор», и откликнуться может
любой из них. Поэтому в коде говорится не «клиент/владелец», а **автор** и
**исполнитель**: один и тот же человек в одном объявлении автор, в другом
исполнитель. Раздел в приложении один на обе роли (`ListingsPage`, две
вкладки: доска и свои).

Ограничение ровно одно: своё объявление взять нельзя. Проверки роли на
`/listings/{id}/take` НЕТ и быть не должно — раньше там стоял `owner`, и
объявление владельца висело мёртвым: взять его не мог никто.

Телефон в объявлении открывается **только после подтверждения** и только
двоим — автору и подтверждённому исполнителю. Не на «взял»: иначе, чтобы
получить номер, хватило бы нажать кнопку, и подтверждение теряет смысл.
Решает это сервер (`can_see_phone`), приложение только показывает результат.

### Стройматериалы

Четвёртый способ, добавлен 3 сентября 2026: клиент покупает **товар**, а не
арендует технику. Кирпич, газоблок, цемент, песок, щебень, арматура — справочник
в `app/core/material_types.py`, тот же принцип, что и с типами техники: в базе
код, на экране название из перевода.

Почему отдельные таблицы (`material_products`, `material_orders`), а не тип
техники: аренда считает «цена за сутки × дни», товар — «цена за единицу ×
количество». В один справочник их не свести — кирпич на три дня бессмыслица,
и эскроу считался бы неверно.

- **Товар проходит модерацию.** Продавец добавляет, админ подтверждает
  (`materials.php`). Неподтверждённый товар в каталоге не виден и купить его
  нельзя. Правка цены или веса снова отправляет товар на проверку: иначе
  подтверждённый товар потом подменяется на что угодно.
- **Машину подбирает сервер по весу** — `app/core/delivery_vehicles.py`.
  5 000 кирпичей = 17,5 т → Howo. Пользователь может выбрать другую машину,
  тогда считаются рейсы: у Labo (0,7 т) это 25 рейсов, и доставка растёт
  во столько же раз. Вес единицы задаёт продавец, от него всё и зависит.
- **Деньги как в аренде**: заказ замораживает сумму на балансе покупателя,
  доставка списывает и переводит продавцу, отмена и отказ только снимают
  заморозку. Комиссию платит **продавец**, считается тем же
  `pricing_service.calculate_commission` — настройка одна на всё.
- **«Доставлено» жмёт ПОКУПАТЕЛЬ**, не продавец. Иначе продавец забирал бы
  деньги, ничего не привезя.
- Расчёт для экрана — `POST /materials/quote`, он же вызывается при создании
  заказа. Формула одна: иначе на экране одна сумма, а спишется другая.

### Объявления: отклик и предложение цены

В объявлениях два пути ответа, и оба нужны:

- **«Взять»** — согласие на бюджет автора (как было).
- **«Предложить цену»** (`listing_offers`) — исполнитель называет свою сумму,
  автор выбирает из пришедших. Одно предложение на человека: повторное
  обновляет старое, а не плодит новые. Принятие предложения сразу переводит
  объявление в `confirmed` — выбор автором и есть подтверждение, промежуточный
  `taken` тут не нужен.

Исполнитель видит **только своё** предложение, все — только автор и админ:
иначе исполнители сбивали бы цену друг другу. Телефон предложившего
открывается автору только **после принятия**, по тому же правилу, что и в
самом объявлении.

**Лайки и закладки** — `listing_reactions`, одна таблица на оба вида, разница
в `kind`. Счётчики НЕ денормализованы: считаются одним `GROUP BY` на страницу.
Колонка вроде `likes_count` рано или поздно разошлась бы с правдой.
Просмотры (`views_count`) остались колонкой, как были, и лайк их **не
накручивает** — за этим следит отдельная проверка в тестах.

## Backend

FastAPI, Python 3.11+. Точка входа `backend/app/main.py`.

Слои: `routes/` (HTTP) → `services/` (логика) → `models/` (SQLAlchemy) + `schemas/` (Pydantic).

Роуты монтируются с префиксами: `/auth`, `/users`, `/companies`, `/equipment`, `/orders`,
`/requests`, `/listings`, `/materials`, `/chats`, `/messages`, `/reviews`, `/payments`,
`/payouts`,
`/notifications`, `/balance`, `/settings`, `/admin`. Плюс `/health`, `/` и `/static`.
Swagger на `/docs` — **автоматически отключается при `APP_ENV=production`**.

Порядок роутов важен: конкретный путь объявляется РАНЬШЕ параметрического.
`/equipment/types` до `/equipment/{id}`, `/notifications/devices` до
`/notifications/{id}`, `/listings/feed`, `/listings/mine` и `/listings/saved` до
`/listings/{id}`, `/materials/types` и `/materials/products/mine` до
`/materials/products/{id}` — иначе FastAPI пытается разобрать слово как число.
На этом уже ловились трижды.

Загруженные файлы лежат в `backend/media/`, раздаются с `/static/`. Путь и
правила (разрешённые расширения, размер, имя файла) — в `app/core/media.py`,
там же удаление. Имя файла **задаёт сервер**: в присланном может быть `../`.

Внешние интеграции:
- **Rahmat (Multicard)** — ЕДИНСТВЕННЫЙ платёжный шлюз
  (`services/rahmat_service.py` — протокол, `services/rahmat_payment.py` —
  баланс и идемпотентность, колбэк `/balance/rahmat/callback`, вебхук
  `/balance/rahmat/webhook`). Через него же идут выплаты на карту
- **Eskiz** — SMS и OTP-коды (`services/eskiz_service.py`, токен кэшируется в таблице `eskiz_token`)
- **Telegram** — уведомления в группу (`services/telegram_service.py`) и
  **вход по боту** (`services/telegram_auth_service.py`): код приходит в
  Телеграм, а при первом входе кода нет вовсе — человек жмёт кнопку и
  делится номером. Бот не может написать первым и не умеет искать по
  номеру, поэтому первый шаг всегда за человеком: `/auth/telegram/start`
  отдаёт ссылку `t.me/<бот>?start=<токен>`
- **Firebase Cloud Messaging** — push (`services/push_service.py`, HTTP v1).
  Без `FCM_PROJECT_ID` и `FCM_CREDENTIALS_FILE` молчит и ничего не ломает

Подробности по деньгам — `docs/backend/PAYMENTS.md`, по уведомлениям —
`docs/backend/NOTIFICATIONS.md`.

Дампы БД — `backend/scripts/backup.sh` и `restore.sh`. Настройки подключения
берутся из `DATABASE_URL`, а не из отдельных `POSTGRES_*`: второй источник
правды разъезжается с первым, что уже случилось — скрипты падали на чужих
значениях по умолчанию.

Обновления бота приходят двумя путями, и в проде нужен именно второй:

- `TELEGRAM_POLLING=true` — сервер сам спрашивает Телеграм. Годится для
  разработки: публичный адрес не нужен, туннель может умирать.
- `/auth/telegram/webhook` — Телеграм присылает сам. **В проде только
  так**, потому что опрос стартует в КАЖДОМ процессе uvicorn, а их
  несколько: два опроса одного бота дают 409, и вход работает через раз.
  Ставится `scripts/telegram_webhook.py set <https-адрес>`.

Адрес вебхука закрыт `TELEGRAM_WEBHOOK_SECRET`. Пустое слово — адреса
нет вообще (404), и это не мелочь: на этом пути не спрашивают ни пароля,
ни кода, поэтому открытый адрес означал бы вход под любым номером по
поддельному `contact`. Сторожит `tests/verify_telegram_webhook.py`.

Администратора на чистой базе нет — `scripts/create_admin.py`. Раньше
вместо него в документах предлагался SQL-INSERT с готовым хешем, а хеш
оказывался от другого пароля, и почему не пускает — не видно.

Выкат в прод: **чистый сервер — комплект `deploy/`** (`deploy/README.md`,
один скрипт настраивает всё под Ubuntu 24.04), дальнейшие обновления и
ручные шаги — **`docs/RELEASE.md`**. Старые семь деплой-документов в
`docs/backend/` пересекаются и написаны до всех изменений, а
`backend/scripts/quick_deploy.sh` и `deploy_movex_004_uz.sh` ставят
`python3.11` и Apache: в Ubuntu 24.04 такого пакета нет, они падают на
первом `apt install`.

Команды (из `backend/`, есть `Makefile`):

```bash
make install                       # pip install -r requirements.txt
make run                           # uvicorn app.main:app --reload --port 8000
python scripts/init_db.py          # ТОЛЬКО первая установка на пустой базе
make migrate                       # alembic upgrade head — обновление схемы
bash tests/run_all.sh              # все проверки (нужен запущенный сервер)
```

Схема **не создаётся при старте приложения**. Раньше там был
`Base.metadata.create_all()`, из-за него база расходилась с Alembic и
`alembic upgrade head` на чистой базе падал.

## Admin

Чистый PHP без фреймворка, подключается к той же PostgreSQL напрямую через PDO —
**не через API бэкенда**. Схему БД меняешь в `backend/` — проверь, не сломались ли
запросы в `admin/*.php`.

Страницы: `index.php` (дашборд), `users.php`, `orders.php`, `requests.php`
(заявки и предложения), `listings.php` (объявления), `equipment.php`
(техника на карте и списком), `materials.php`, `balance.php`, `budget.php`,
`commission.php` (ставка комиссии), `payouts.php` (заявки на вывод денег),
`system.php`, `backup.php` (дампы БД), `login.php`/`logout.php`.
Конфиг — `admin/config.php`.

`equipment.php` — карта на Leaflet: слой «спутник» (Esri World Imagery с
подписями улиц сверху) и обычная карта OSM. Оба работают **без ключа** —
ключ Яндекса из мобилки для MapKit и в вебе не годится, для Yandex JS API
нужен отдельный. Два слоя точек: техника (`equipment.latitude/longitude`) и
точки доставки активных заказов (`orders.delivery_*`), между связанными
точками — пунктир.

**Точка техники — НЕ текущее местоположение машины.** Это адрес, который
владелец выбрал при добавлении, и он не меняется. Поэтому в карточке точки
показан её возраст («30 kun oldin yangilangan»), а над таблицей висит
предупреждение: иначе карту прочитали бы как живое слежение. Настоящий
real-time требует, чтобы приложение слало координаты с телефона — такого в
проекте нет вообще.

Возраст точки считается в PHP (`pointAge`), не в JavaScript: PostgreSQL
отдаёт смещение вида `+05` без минут, и `new Date()` такую строку не
разбирает — в карточках стояло «sana noma'lum».

Мелочь, на которой эта страница сразу упала: клиент в `orders` — это
`user_id`, а не `client_id`, хотя в коде везде говорится «client».

**Каждая форма с POST обязана нести CSRF-токен, а страница — вызывать
`requireCsrfToken()` сразу после `requireAdmin()`.** Панель живёт на одних
cookie, а их браузер прикладывает к запросу с любого сайта: без этой проверки
достаточно было открыть чужую страницу, будучи залогиненным, — и от имени
админа удалялись пользователи, менялись пароли, подтверждались выплаты.
Проверки не было нигде. Сторожит `backend/tests/verify_admin_csrf.py`: он
читает файлы и валится, если появилась форма или страница без токена.

`requests.php` и `listings.php` в основном показывают: выбрать исполнителя —
дело клиента, админ не решает за него. Единственное действие в объявлениях —
закрыть (для спама). В меню два счётчика: открытые заявки **без единого
предложения** и объявления, которые взяли, но клиент ещё не подтвердил.

В проде панель живёт на **`/panel/`** основного домена, а не на
поддомене `admin.<домен>`: `movex.004.uz` сам по себе третьего уровня, и
`admin.movex.004.uz` — уже четвёртого, такую запись даёт не всякий
регистратор. На `/admin` её положить нельзя — путь занят роутером API.
Работает без правок, потому что все ссылки внутри относительные
(`index.php`, `assets/…`, `header('Location: login.php')`); nginx отдаёт
её через `root` + симлинк `panel → admin`, а не через `alias`: alias с
вложенным location для php даёт неверный `SCRIPT_FILENAME`. Режим
переключается `ADMIN_MODE=subdomain` в `deploy/bootstrap_ubuntu24.sh`.

`admin/config.php` берёт доступ к БД из `backend/.env`, из `DATABASE_URL`.
Раньше он читал `POSTGRES_*`, которых в проекте нет, и падал на чужих
значениях по умолчанию — вся панель отдавала «role does not exist».

`payouts.php` дублирует логику движения денег из `payout_service.py`. Меняешь
одно — меняй и второе, иначе панель и API разойдутся.

Тип техники в базе — **код** (`excavator`). В интерфейсе показывай
`equipmentTypeName()` из `config.php`, на бэкенде — `type_name()`. Код уже
трижды просачивался к пользователю: в заголовке уведомления, в описании
транзакции и в таблицах админки. `verify_equipment_types.py` теперь ищет
`{equipment.type}` внутри f-строк и валит сборку.

## Mobile

Flutter 3.8, Dart SDK `^3.8.1`. 93 dart-файла, 43 экрана.

Структура: `lib/core/` (сеть, модели, сервисы, тема, роутер, виджеты) +
`lib/features/{auth,client_home,owner_home,balance,settings,requests,listings,notifications}/presentation/pages/`.

- Навигация — **go_router**, все маршруты объявлены прямо в `lib/main.dart`
- Нижнее меню — по пять вкладок у каждой роли, объявлены списком в
  `client_home_page.dart` и `owner_home_page.dart`. **Номера вкладок у
  владельца — константы `OwnerTab`**, потому что дашборд переключает страницы
  по номеру: там стояли голые `2` и `3`, и добавление одной вкладки молча
  увело кнопки не туда
- Состояние — **provider**
- HTTP — **dio**, единственный клиент `lib/core/network/dio_client.dart`
  (интерцептор подставляет Bearer-токен из SharedPreferences, на 401 чистит сессию и кидает на `/login`)
- Карты — **yandex_mapkit**, только Android и iOS. В браузере плагина нет
  вообще: `YandexMap` там не рисует ничего, а в консоль падает
  `unregistered view type`. Все 10 мест обёрнуты в `MapOrPlaceholder` — на
  телефоне карта, в вебе объяснение вместо пустоты. Главная клиента на вебе
  сразу открывает список.
  Ключ задаётся в двух местах: `MainActivity.kt` (Android) и
  `AppDelegate.swift` (iOS). Забудешь про iOS — карта на iPhone просто не
  запустится, именно так и было
- Локализация — **easy_localization**, переводы в `assets/translations/` (uz по умолчанию).
  Строку в интерфейсе писать только через `.tr()`: QA находил, что половина
  русского интерфейса оставалась узбекской из-за текста, записанного прямо в
  коде. Проверка — `python3 tool/verify_translations.py`
- Ключ перевода, положенный в переменную, тоже надо перевести. `PermissionService`
  возвращал `errorMessage` с ключом внутри, а диалог печатал его как есть — на
  экране виднелось `messages.location_permission_not_granted_message`. Поле
  называется `messageKey`, показывать через геттер `message`. Проверка это ловит
- Цена приходит с сервера **строкой** (`"1100000.00"`). Сравнивать и сортировать
  только через `pricePerDayValue` и соседние геттеры: `compareTo` на строках
  ставит `"950000.00"` выше `"2800000.00"`
- Поле телефона (`phone_input_field.dart`) уже содержит `+998 `, вводятся
  только 9 цифр. Любая запись номера приводится к одному виду функцией
  **`normalizeUzbekPhoneDigits`** — она одна на поле, проверку и отправку:
  `+998901234567`, `998901234567`, `00998901234567`, `+998 90 123 45 67`,
  `(90) 123-45-67`, `901234567` дают одинаковый результат.
  Правила: видимый префикс `+998` снимается ПЕРВЫМ (иначе он попадает в
  цифры и при наборе посимвольно копится сам в себя), затем `00998`/`998`,
  затем старый внутренний `8`.
  **`LengthLimitingTextInputFormatter` тут ставить нельзя.** Он обрезает
  строку ДО нормализации, и правило «убрать повторный 998» (оно срабатывает
  только на длине больше 9) не выполняется никогда. Именно из-за него
  набранный `+998901234567` застревал на `998998901234` — чужой номер,
  который проверку ПРОХОДИЛ, и человек молча уезжал на регистрацию.
  Вставка такого номера при этом просто стирала поле.
  Сторожит `backend/tests/verify_phone_normalization.py`
- Тип техники — **код из справочника** (`lib/core/constants/equipment_types.dart`),
  а не свободный текст. В интерфейсе всегда показывай `EquipmentTypes.label(code)`,
  иначе пользователь увидит `excavator` латиницей. Так уже было четыре раза,
  последний — заголовки карточек на главной клиента. `verify_equipment_types.py`
  теперь читает и dart-файлы, не только бэкенд
- Картинку с сервера показывай через `AppConfig.mediaUrl(path)`. Сервер отдаёт
  `/static/…` — путь от корня, `Image.network` его не понимает и рисует пустоту.
  Фото техники так и не работали ни разу: раздачи `/static` не было вообще, а
  приложение отдавало относительный путь

### Сборка под iPhone

Собирается и проверено 3 сентября 2026 на этой машине: Xcode 26.6, macOS 26.2,
Apple M1. Результат — `build/ios/iphoneos/Runner.app`, 86 МБ, arm64,
`uz.movexgo.app`, минимум iOS 15.0.

Путь занял шесть препятствий подряд, и **ни одно не было в коде проекта**.
Все записаны здесь, чтобы не проходить заново:

1. **Xcode 26 ставится без платформ.** iOS SDK в комплекте есть, а платформы
   нет, и `xcodebuild` говорит «Found no destinations for the scheme Runner».
   Лечится `xcodebuild -downloadPlatform iOS` — это 8,5 ГБ. Flutter при этом
   пишет невнятное «No Xcode build settings have been found».
2. **Минимальная версия iOS — 15.0, и её нельзя выдумывать.** Цифра лежит в
   `Flutter.xcframework/ios-arm64/Flutter.framework/Info.plist`, ключ
   `MinimumOSVersion`. Меньшая ломает `pod install` сообщением «required a
   higher minimum deployment target», не называя виновника. Задана в трёх
   местах `project.pbxproj` и в `ios/Podfile` (там же `post_install`, который
   поднимает планку каждому поду отдельно — `flutter_additional_ios_build_settings`
   чинит не всех).
3. **`Info.plist` обязан описывать камеру и галерею.** `image_picker`
   используется для фото техники, объявлений и материалов; без
   `NSCameraUsageDescription` и `NSPhotoLibraryUsageDescription` приложение
   на iPhone не «ругается», а **падает** при открытии галереи, и App Store
   такую сборку не принимает.
4. **`yandex_mapkit 3.4.0` не собирается новым SDK.** Внутри используется
   `TARGET_IPHONE_SIMULATOR` — макрос, убранный Apple из видимости Swift в
   iOS 26 SDK.

   **Нативная библиотека карт на Android поднята до `maps.mobile:4.19.0-full`**
   (строка в `third_party/yandex_mapkit/android/build.gradle`). Она отдельна
   от версии flutter-плагина, поэтому dart-код и все 11 файлов с картой
   остались нетронутыми. Причина: Google Play не принимает релиз, пока
   `libmaps-mobile.so` выровнена под 4 КБ, а 16 КБ появились ровно в 4.19.0
   — в 4.18.0 ещё 4 КБ, проверено перебором версий.

   Апгрейд потребовал правок в java-части плагина, API за 15 версий
   разошлось: `SearchFactory`/`TransportFactory`/`DirectionsFactory` больше
   не принимают `Context` (`initialize()` убран совсем), `createDrivingRouter`
   требует `DrivingRouterType`, `setHeadingEnabled` переименован в
   `setHeadingModeActive`, у `GeoObjectSelectionMetadata` и `RequestPoint`
   добавились поля, `SuggestListener.onResponse` принимает `SuggestResponse`
   вместо списка. Сигнатуры брались не наугад — читались из самого `.aar`
   через `javap`.

   **Из-за карт `minSdk` поднят с 24 до 26**: 4.19.0 ниже Android 8.0 не
   работает. Телефоны на Android 7.x приложение в магазине не увидят. Правленая копия лежит в `mobile/third_party/yandex_mapkit`
   и подключена через `dependency_overrides`; отличается от оригинала **ровно
   одним файлом** (`ios/Classes/YandexMapController.swift`, проверка на
   симулятор переписана на `#if targetEnvironment(simulator)`), android- и
   dart-части побайтово те же.
   Наверх, до 4.x, сознательно НЕ обновлялись: это мажорная версия, карту
   используют 11 файлов, а на Android она работает. `~/.pub-cache` не правится
   принципиально — он общий для всех проектов и затирается `flutter pub get`.
   `third_party/**` исключён из `analysis_options.yaml`, иначе `flutter analyze`
   растёт с 225 до 291 и хоронит собственные предупреждения.
5. **Flutter из Homebrew несёт `com.apple.quarantine`.** `codesign` отказывается
   подписывать помеченные файлы. Снимается один раз:
   `xattr -dr com.apple.quarantine /opt/homebrew/share/flutter`.
6. **Каталог сборки не должен лежать в iCloud.** На этой машине `~/Desktop`
   синхронизируется (`FXICloudDriveDesktop = 1`), а проект внутри. iCloud вешает
   на созданные папки `com.apple.FinderInfo` и `com.apple.fileprovider.fpfs#P`,
   и подпись падает с «resource fork, Finder information, or similar detritus
   not allowed». Причём метка садится на ПАПКУ `Flutter.framework`, а Flutter
   чистит только бинарник внутри — поэтому его собственная чистка не спасает.
   Обход: `mobile/build` сделан симлинком на `~/Library/Caches/movex-flutter-build`
   (`~/Library` iCloud не трогает). Симлинк локальный, в git не попадает.
   Тот же корень объясняет, почему прямой `xcodebuild` собирал успешно: он
   пишет в `~/Library/Developer/Xcode/DerivedData`, то есть уже вне iCloud.

Собранное приложение **не подписано** — оно доказывает, что код компилируется,
но на живой iPhone не встанет. Для установки нужен Apple ID в Xcode

## Деньги: как это работает и почему так

Денежный контур переписан 30 августа 2026 после того, как обнаружились три способа
получить чужие деньги. Правила, которые нельзя нарушать при доработках:

- **Цену считает только сервер** — `services/pricing_service.py`. `total_amount` и
  `commission` из тела запроса игнорируются: раньше клиент присылал свои цифры и
  сервер им верил, экскаватор на месяц уходил за 1 000 сум. Формула обязана совпадать
  с расчётом в `rent_equipment_page.dart`, иначе клиент увидит на экране одну сумму,
  а спишется другая.
- **Комиссию платит владелец, а не клиент.** Клиент платит аренду и доставку;
  доля платформы удерживается из выплаты владельцу при завершении заказа.
  Два режима в `app_settings`: `commission_mode` = `fixed` (сейчас, 5 000 сум
  из `commission_fixed`) или `percent` (`commission_percent`, 10%).
  Переключается в админке — `commission.php`, кода не трогать.
  Комиссия **никогда не превышает сумму заказа**: иначе на дешёвом заказе
  баланс владельца ушёл бы в минус — он платил бы за то, что поработал.
- **Баланс пополняется только по подтверждению платёжной системы.** Заявка всегда
  создаётся в статусе `pending`, зачисляет её колбэк `/balance/rahmat/callback`
  (или вебхук со статусом `success`).
  Список разрешённых способов — `SELF_SERVICE_PAYMENT_METHODS` в `balance_service.py`.
  Добавлять туда способ можно, только если по нему приходит подтверждение оплаты.
  Колбэк ИДЕМПОТЕНТЕН: Multicard повторяет его после таймаута или HTTP 500, и
  повтор не должен зачислить деньги второй раз. Сумма из колбэка сверяется с
  суммой транзакции, подпись проверяется всегда — адрес открытый.
- **При завершении заказа деньги списываются с баланса клиента, а не только
  размораживаются.** В ветках отказа и отмены — наоборот, снимается только заморозка.
  Перепутать эти два случая = печатать деньги.
- **Баланс блокируется через `with_for_update()`** при создании заказа, иначе два
  одновременных запроса замораживают одну и ту же сумму дважды.

**Бонус за регистрацию.** Новый пользователь с ролью `owner` получает
подарок на баланс сразу при регистрации — транзакция типа `bonus`
(`balance_service.grant_signup_bonus`).

Начисление выдаётся ТОЛЬКО в `/auth/register`, то есть зарегистрированные
раньше владельцы не получили ничего. Доначислить им — разовый скрипт
`backend/scripts/grant_bonus_to_existing_owners.py`: без флагов показывает
список и сумму, деньги двигает только с `--apply`. Он идемпотентен, признак
«уже получил» — транзакция типа `bonus`, а не остаток на балансе: подарок
могли потратить, и проверка по балансу выдала бы его второй раз. Само
движение денег не продублировано — и регистрация, и скрипт зовут
`balance_service.credit_bonus`, иначе в одной из копий забыли бы поднять
`bonus_balance` и подарок стало бы можно вывести на карту. Сумма и включение лежат в
`app_settings` (`signup_bonus_amount`, `signup_bonus_enabled`, по умолчанию
50 000 и включено) и меняются в `commission.php` — не в коде. Тип `bonus`
пришлось добавить в CHECK-ограничение `check_transaction_type` отдельной
миграцией: без неё INSERT падал, баланс пополнялся, а транзакции не было.
Ошибка выдачи НЕ ломает регистрацию, но пишется в лог — немой `except`
именно это и скрывал.

**Бонус НЕЛЬЗЯ вывести на карту.** Его неизрасходованная часть лежит в
`balances.bonus_balance`, и к выводу доступно `balance - frozen -
bonus_balance`. Иначе с каждой новой сим-карты уходило бы 50 000 живых
денег: зарегистрировался, вывел, бросил аккаунт.

Правило «сначала тратятся свои деньги, потом бонус» держится **одним**
слушателем `before_flush` в `app/models/balance.py`: перед любой записью
`bonus_balance` подрезается до `balance`. Списаний в коде семь (заказы,
материалы, объявления, возврат платежа, вывод), и проверка в каждом рано или поздно
где-нибудь забылась бы.

Приложению сумма бонуса отдаётся отдельным полем: экран вывода считает
`withdrawableBalance` сам, и без этого поля он показывал бы деньги, которые
не выводятся.

Вывод денег владельцу — `payout_requests` и `/payouts/*`. Заявка замораживает
сумму, выплата списывает, отказ снимает заморозку.

**Деньги на карту уходят через шлюз, а не руками.** `payout_service.send_to_card`
зовёт `POST /payment/credit` Multicard, и с баланса списывается ТОЛЬКО после
ответа `success`. Порядок обратный — сначала списать, потом перевести — оставил
бы владельца без денег при неудачном переводе. Если результат неизвестен
(таймаут или `ERROR_UNKNOWN`), повторять запрос НЕЛЬЗЯ: документация требует
спросить статус (`GET /payment/credit/{uuid}`), иначе по одной заявке уйдёт
две выплаты. Для этого есть `/payouts/{id}/sync` и кнопка в панели.

Кто нажимает — настройка `payout_auto_enabled` в `app_settings`: выключено
(по умолчанию) — админ, включено — система сразу при создании заявки.

`admin/payouts.php` больше НЕ двигает деньги сам: он зовёт
`/payouts/internal/{id}/pay|reject|sync` с заголовком `X-Admin-Secret`
(`ADMIN_INTERNAL_SECRET`). Так дублирование логики, из-за которого панель и
API могли разойтись, исчезло совсем. Пустое слово — внутренних адресов нет
(404), как у телеграм-вебхука.

- **За вывод удерживается своя комиссия, и платит её владелец.** Причина: с
  заказа берётся всего 5 000, и этого не хватает на процент платёжной системы
  за перевод на карту. У неё **отдельный** тумблер, не связанный с комиссией
  за заказ: `payout_commission_mode` = `fixed` (5 000) или `percent` (10%),
  вместе не работают. Настраивается в `commission.php`, считается в
  `payout_service.calculate_commission`.
- **Удерживается ИЗ суммы заявки, а не сверх.** Просит 100 000 — с баланса
  уходит 100 000, на карту приходит 95 000. Так владелец может вывести баланс
  до нуля; при удержании сверху полный баланс вывести было бы нельзя.
  Замораживается и списывается **полная** сумма — разница остаётся платформе.
- **Комиссия и сумма к перечислению пишутся в заявку** (`commission`,
  `payout_amount`), а не вычисляются при показе. Иначе смена ставки задним
  числом переписала бы историю: заявка, поданная при 5 000, показывалась бы
  с 10%.
- Комиссия **никогда не больше суммы заявки**, и заявка, где на карту
  осталось бы ноль, отклоняется целиком — иначе владелец отдаёт деньги и не
  получает ничего.
- Формула в `PayoutSettingsModel.commissionFor` (`payout_model.dart`) обязана
  совпадать с серверной: приложение показывает расчёт до отправки заявки.
  Ставку оно берёт из `GET /payouts/settings`, а не хранит у себя — иначе
  в собранном APK застынет старое значение.

## Два способа заказа

В приложении их два, и они работают параллельно.

**Каталог.** Клиент выбирает конкретную машину конкретного владельца, заказ
уходит этому владельцу. Цена известна сразу — ставка из карточки.

**Заявки** (`equipment_requests`, `request_offers`, `/requests/*`). Клиент
называет ТИП техники, даты, место и свой бюджет. Заявку видят все владельцы
подходящей техники в радиусе, каждый отвечает своей ценой, клиент выбирает
одно предложение — и только тогда создаётся обычный заказ.

Правило, которое нельзя нарушать: **заявка и предложение не двигают деньги.**
Бюджет клиента — ориентир, цена в предложении — запрос владельца. Реальная
сумма считается в момент выбора предложения, внутри `create_order`, по
`pricing_service`. Ставка берётся из сохранённой записи `request_offers`
через `price_per_day_override` — из тела запроса её передать нельзя.

Тип техники в заявке проверяется строго, `normalize_type` там не
используется: он превращает незнакомый текст в `other`, а от типа зависит,
кому уйдёт уведомление.

**Радиус** — `users.search_latitude/longitude/search_radius_km`. Владельцу
ограничивает ленту заявок, клиенту — область поиска. Точка не задана — фильтр
не применяется: не настроивший радиус не должен остаться без данных.

Проверки: `bash tests/run_all.sh` — 21 набор, ~450 проверок (точное число плавает: часть тестов считает по данным) плюс смоук по GET-эндпоинтам
смоук-теста, против живого сервера.

**Токен входа не истекает.** `ACCESS_TOKEN_EXPIRE_MINUTES=0` означает, что
в JWT вообще нет поля `exp` (`create_access_token`). Раньше в `.env` стояло
1440, и человек, вернувшийся на следующий день, видел экран входа заново —
он считал, что приложение «не запоминает». Телефон теперь защищает пин-код
и биометрия в самом приложении, а не срок жизни токена. Заблокированный
аккаунт по-прежнему отключается СРАЗУ: это проверяет `get_current_user`,
к сроку отношения не имеет.

`OTP_TEST_MODE=true` кладёт код прямо в ответ. Для админского номера код
**не отдаётся никогда**: иначе любой, до кого дошёл адрес сервера, забирает
админский токен — телефон известен, код спрашивается запросом. Тесты берут
админский код из базы, `tests/_auth.py`.

## Права доступа

Правило в одном месте — `app/core/access.py`. Раньше проверок владения не было
почти нигде, и любой авторизованный пользователь мог читать чужие заказы и
переписку, менять чужой телефон и удалять чужие аккаунты.

- участники заказа — клиент и владелец техники; они видят свой заказ, свою
  переписку и профиль друг друга (иначе им не созвониться);
- списки (`/orders/`, `/chats/`, `/payments/`, `/notifications/`) всегда
  фильтруются по текущему пользователю;
- телефон при правке профиля приводится к виду `998901234567`
  (`to_db_phone`): вход ищет номер без `+`, и профиль, сохранённый как
  `+998901234567`, закрывал человеку доступ к собственному аккаунту.
  Заодно это чинило проверку занятости — `+998…` и `998…` считались
  разными строками, то есть чужой номер можно было забрать себе;
- удаление заказов, чатов, платежей и пользователей — только админ;
- `/users/` целиком — только админ.

Добавляешь эндпоинт со списком или доступом по id — используй хелперы из
`access.py`, не пиши проверку заново.

## Известные проблемы

Актуально, ещё не исправлено:

1. **Пароль от FTP скомпрометирован** — `mobile/.vscode/sftp.json` лежал в
   архиве открытым текстом. В git не попадает, но пароль надо сменить на сервере.
2. **Push-уведомления не отправляются.** Серверная часть написана целиком
   (`services/push_service.py`, FCM HTTP v1) и подключена ко всем событиям.
   Не хватает проекта Firebase: его может создать только владелец
   Google-аккаунта. Порядок — `docs/backend/NOTIFICATIONS.md`.
3. **Боевых мерчант-ключей Rahmat нет.** Интеграция написана и проверена
   живой оплатой на ПЕСОЧНИЦЕ (`rhmt_test`, карта 8600 5333 6409 8829).
   Что вписать и куда — в `docs/backend/PAYMENTS.md`.
4. **Депозит Multicard для выплат не пополнен.** Выплаты владельцам идут из
   кошелька приложения; на бою без пополнения `POST /payment/credit` вернёт
   ошибку. Остаток — `GET /payment/application`.
5. **`POST /users/` не приводит телефон к виду `998…`** — в отличие от
   `/auth/register`, который зовёт `to_db_phone`. Импорт в файле есть, а
   вызова нет. В базе уже лежит один такой номер с плюсом, и этот человек
   в свой аккаунт не войдёт: вход ищет номер без плюса. Тот же эндпоинт не
   выдаёт бонус, даже когда создаёт владельца.
6. **`user_service.create_user` — мёртвый и сломанный.** Не вызывается
   ниоткуда (роут `/users/` пишет свою вставку) и упал бы при вызове:
   передаёт `hashed_password` в модель, где поле называется
   `password_hash`, и не заполняет обязательный `role`.
7. **Живого местоположения техники нет.** `equipment.latitude/longitude` —
   статическая точка, выбранная владельцем при добавлении. Приложение
   координаты никуда не шлёт, таблицы позиций нет. Карта в админке честно
   показывает возраст точки; настоящее слежение — отдельная работа на
   стороне мобилки.
8. **Франшизы на бэкенде нет вообще** — ни эндпоинта `/franchises/`, ни
   модели, ни таблицы. Экран показывал цифры, собранные из чужих эндпоинтов,
   то есть выдуманные. Сейчас он честно пишет, что раздел не подключён;
   1228 строк кода оставлены нетронутыми — включить обратно можно флагом
   `_backendReady` в `franchise_manage_page.dart`. Удалить их или написать
   бэкенд — продуктовое решение.
9. **Ключ Яндекс-карт лежит в исходниках** — в `MainActivity.kt` и как запасное
   значение в `AppDelegate.swift`. Для клиентского ключа это обычная практика:
   он всё равно уезжает внутри APK, и вынос в конфиг сборки ничего не скрывает,
   только позволяет менять ключ между сборками. Трогать без Android SDK и
   полного Xcode рискованно — правки Gradle и Xcode нечем проверить.
10. **`equipment.type_legacy`** — временная колонка с исходным текстом типа до
   миграции. Когда данные проверят, удалить отдельной миграцией.

## Окружение этой машины

- Бэкенд работает на **Python 3.12** (venv в `backend/venv`), PostgreSQL 16 ✅, PHP 7.4 ✅
- **Flutter 3.47.2** ✅, Chrome ✅
- **Собрать под телефон**: полного Xcode с CocoaPods нет (стоят только
  Command Line Tools). Android SDK ставится через
  `brew install --cask android-commandlinetools`. JDK 17 и 21 в системе есть;
  Flutter направлен на 21, потому что с 23 у Android Gradle Plugin бывают
  сюрпризы
- Android с 9-й версии блокирует HTTP. Для проверки на локальном сервере
  адрес машины должен быть в
  `android/app/src/main/res/xml/network_security_config.xml` — **точно**,
  `includeSubdomains` для IP не работает. Прод по HTTPS, ему это не нужно
- Веб-сборка работает и годится как проверка: `flutter build web --release`
  компилирует весь код. Карта на вебе не заработает (yandex_mapkit только
  под телефоны), остальное рисуется

Перед коммитом в мобилку:

```bash
cd mobile && flutter analyze          # должно быть 0 ошибок
flutter build web --release           # быстрая проверка, что всё компилируется
```

`flutter analyze` показывает ~227 замечаний из прежнего кода (print в проде,
устаревший withOpacity, мёртвые проверки на null). Ошибок — ноль. Не увеличивай
это число своими правками.

## Правила

- Секреты — только в `.env` и переменных окружения, никогда в код и никогда в git
- Меняешь схему БД — миграция Alembic **и** проверка PHP-запросов в `admin/`
- Трогаешь деньги или права доступа — прогони `bash backend/tests/run_all.sh`
  и допиши проверку на то, что изменил
- Языки в проекте смешаны: код и комментарии на узбекском, русском и английском.
  Не переписывай существующие комментарии ради единообразия
